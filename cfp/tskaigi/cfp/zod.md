# タイトル
同じバリデーションを、あえて2回書いた話

## 概要
フロントエンドとバックエンドで同じビジネスルールを扱いながら、Zod スキーマを共有せず別々に定義しました。実行環境と信頼レベルの違いを明確にするための設計判断です。

## 背景
フォーム用のスキーマと、Lambda 上で動く API 用スキーマの両方で、同じ加算率・加算額の排他制約を表現していました。

## 問題
UI 用フィールドやネスト構造が API 側に混入し、信頼境界が曖昧になるリスクがありました。

## 気づき・判断
UX のための検証と、防御のための検証は別の責務だと整理し、あえて二重に定義しました。

## 聴講者への学び
フロントとバックで Zod スキーマを分けた理由と、信頼境界ごとにバリデーションを設計する具体例を知ることができます。

### 対象となるロール
フロントエンド／バックエンド／フルスタックエンジニア

### 想定レベル
中級
TypeScript でフロント・バック双方のバリデーション設計に関わる方
